# ADR 0035: Android confirmed paycheck lines and hours

Status: accepted for bounded implementation. October 22, 2026. Native device and release evidence remain separate gates.

[Android local state](0030-android-local-native-state-and-export.md) · [Portable state](0034-portable-financial-state.md) · [Shared line contract](../../shared/contracts/reconciliation/README.md) · [Payroll coverage](../product/payroll/coverage-and-gaps.md)

## Decision

Android may compare manually identified current-period earnings and hour lines using the existing pure `LinePaycheckAssessor` and its existing configured-rules engine. The worker chooses full-rate versus base-plus-premium layout, actual-work versus paid-equivalent hours, and separate versus included callout mapping. Unconfirmed choices remain unconfirmed. Entered decimal observations are source assertions; blank is unknown and a typed zero is an observation. The full-breakdown confirmation is independent of work completeness and rule coverage.

The native profile still records regular work and its existing configured daily tier, outside-schedule multiplier and optional per diem. This slice introduces no callout work or minimum-guarantee rule. Choosing a statement mapping cannot create a guarantee, determine eligibility, establish legal applicability or clear weekly-rate review. Amounts and hours are different units. Statement dates and payroll timezone must match the frozen target before any comparison; observations remain saved when the result is not comparable.

Schema 6 adds nullable `confirmedLineFacts` to each saved native paycheck receipt. A captured version-1 object contains the explicitly identified statement currency, three mapping enums, four optional earnings amounts, three optional hour values, optional observed per diem and the complete-breakdown flag. Gross, statement period, work completeness and the worker's rule-coverage assertion stay in the receipt's existing source fields. Every new save captures an object, including unconfirmed mappings and no entered lines. It does not treat an unentered line as zero. Decimal input rejects exponent notation, signs, grouping and non-finite values; money is bounded from zero through 1,000,000,000,000, hours through 10,000, both with at most twelve fractional places. Statement currency must be an uppercase three-letter code matching the configured profile; this slice performs no currency conversion and refuses a different currency rather than comparing mismatched money. No binary floating point or new dependency is introduced.

The migration advances schema 5 to 6 without changing existing financial trees or replaying earlier results. Schemas 1–4 first retain their existing documented migrations, including the schema-2 weekly-review safety upgrade; this slice adds no reassessment or new interpretation of those historical inputs. Earlier receipts retain absent/null capture as unknown, never reconstructed from comparisons or empty maps. Earlier schema files that contain a non-null capture are refused. Current files validate the captured DTO's version, closed keys, explicit mapping/confirmation fields and exact decimal observations. Captured receipts replay the original frozen profile, work, source facts and engine, then require exact equality of assessment, comparisons, component IDs, rules, amounts and result metadata. Replay is limited to the recorded capture version; earlier unknown receipts and foreign portable receipts are not recalculated or upgraded. This validates reproducibility, not authorship of an editable backup.

The existing pure engine identifier remains unchanged because its algorithms do not change. The capture object's explicit version identifies the new application input/replay boundary. Saved observations remain immutable; a later paycheck comparison is a new receipt. The pending weekly input remains true and a separate weekly result cannot clear it.

The manual form and history distinguish observed values, expected values and possible differences. Hours display to four places according to the existing assessor; original observations retain their exact decimal strings. Full-rate versus premium-only explanations and coverage wording accompany the choices. History keeps the source mapping, observations, completeness assertion, unit, expected/paid/difference and source component references readable.

Same-client encrypted backups retain the capture. Portable v1 already represents line facts: export maps captured choices and entered observations into its existing typed fields, retains unentered paystub observations as null with markers, and leaves facts that Android did not record null with markers. Compared scope is based on actual saved hourly/earnings-line comparisons, not on entered values or a complete-breakdown assertion; a missing mapping or mismatched period cannot claim confirmed-line comparison scope. All entered facts remain separately retained. Earlier captures stay entirely unknown in the portable line-facts fields. Import continues preserving foreign receipts read-only. No shared-format version or source-history rewrite is needed.

## Independent examples and verification boundary

At a confirmed USD 50/hour rate with a daily 8-hour/1.5× tier, ten hours produce USD 400 regular plus USD 150 overtime, USD 550 total. A statement with USD 350 regular and USD 200 overtime has the same gross but opposite USD 50 line differences; neither cancels the other or clears review. An omitted overtime observation produces no overtime comparison. Calling only USD 400 regular the complete USD 550 breakdown is conflicting earnings, not an inferred zero overtime line. A different confirmed statement period is not comparable, with no expected gross or line comparisons, while all entered source facts remain retained.

Required regressions cover both layouts, hours bases, explicit zero versus blank, source-period mismatch, incomplete and contradictory breakdowns, unusual/unknown mappings, per-diem scope, frozen replay/tamper refusal, schema 1–5 migration, encrypted backup and portable null-marker fidelity. A checked-in Compose journey must exercise entry/save/history/relaunch; only a recorded successful device run establishes that runtime gate. JVM/build/lint, emulator, physical-device, provider and store evidence must be reported separately. No correctness or release pass is asserted by this ADR.
