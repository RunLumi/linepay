# ADR 0034: Portable financial state and explicit profile adoption

Status: accepted for the v2 local-only manual-transfer contract. Client runtime adapters and cross-client device E2E remain separate acceptance gates.

## Context

The iOS, Android, and browser clients keep pay profiles, rules, work, and paycheck evidence in different local models. Their existing backups are client-specific. Wrapping one client's native state in the common password envelope does not make it safe to restore in another client: schemas, current-work identity, supported rule fields, time context, and receipt traces differ.

The owner chose local-only storage and manual export. Cross-client transfer must preserve the full selected financial state, original receipt meanings and identifiers, and original attachments. Missing source fields must remain unknown. Adoption may create a new configured profile, but must not rewrite the imported facts or imply legal coverage.

## Decision

- Keep the existing LPBENC01 authenticated envelope and size limits. Define plaintext `com.streamentry.linepay.portable-state` version 1 in `shared/contracts/portable-state/schema-v1.json`; do not change or reinterpret existing client-local backups.
- Use closed typed records for profiles, versioned rule snapshots and changes, dated timelines, exact period windows, work snapshots/revisions/corrections, frozen paycheck receipts and assessment revisions, weekly-rate results embedded in a supported calculation, and original bytes. The current `source` identifies the exporter; original receipt producers and original record clients/local IDs remain in each receipt and `identityCrosswalk`.
- Require full-source inventory. Export refuses if any saved financial kind, unsupported draft, original, or evidence item cannot be represented. Destination-owned commerce/trial, navigation, diagnostics, and activity state are excluded from the portable file; they do not themselves block export. Unknown kinds, unknown properties, dangling references, target-unpreservable originals, size overflow, or storage-capability failures refuse the entire file. A calculator feature that cannot be activated is reported separately and keeps that context read-only until a distinct adoption/configuration action.
- Treat `fieldsNotRecorded` as source knowledge, not a defaulting hint. Null with a marker is not converted to zero, empty, waived, or confirmed. Financial decimal strings exclude exponent notation and binary floating point. The portable grammar permits 24 integer digits and 128 fractional digits. The latter retains saved repeating calculation traces such as `workedSeconds / 3600`; it is not a user-entry precision limit. Apple documents Foundation `NSDecimalNumber` as a base-10 mantissa of up to 38 digits with exponent −128 through 127 ([Foundation `NSDecimalNumber`](https://developer.apple.com/documentation/foundation/nsdecimalnumber)). The 24-digit integer ceiling is an explicit transfer-format bound rather than the full Foundation range. Clients preserve source decimal string spelling and refuse the whole file if any stored value is outside the wire bounds. Separately, activation review checks selected rule values against the target calculator's exact parser and keeps a retained but unparseable rule read-only pending native configuration. Stored work instants and timezones remain exact; dates-only source boundaries are never converted to invented instants.
- Keep the identity crosswalk stable across restore and re-export. A source work ID may appear in multiple snapshots with different facts; snapshot selection carries the exact historical version, and adapters must not globally deduplicate changed facts.
- Allow up to 100 retained profile snapshots. `activeProfileRef` is the saved global/default profile for new periods; the one known `period.isCurrent=true` record independently selects the current workspace and owns its profile/rules/work references. These may differ. A compatible restore preview may retain/select its source default after explicit replacement confirmation; adoption is not required just to preserve frozen history. Current-work/current-period selection can advance after explicit work or period rollover while prior snapshots and receipts remain unchanged. Future-effective rule changes may remain linked to a period after its work window ends; this configuration metadata does not extend the period's allowed work-time interval. Target activation review resolves each rule-change ID to its immutable target rule snapshot. If material configuration is absent, unsupported for native calculation, or actually edited, create a new profile/rule/period/work context and an explicit `adoptions` record linking source to adopted IDs, confirmation time, and the configured fields reconfirmed. Keep source rules, receipts, work facts, and windows unchanged; update only mutable current-work/current-period selection metadata. The adoption record pins the exact rule snapshots confirmed then; later edits and rollovers do not rewrite that lineage receipt. The new profile points back to its source with `adoptedFromProfileRef`. Adoption records cannot assert legal or weekly applicability through a generic field confirmation; those uncertainties stay explicit.
- Before replacement, each receiver performs complete structural, reference, range, attachment, and target-capability validation. Replacement is whole-file, previewed, explicitly confirmed, and atomic. A failed check or commit leaves existing records and files unchanged.
- Keep the format local. No account, backend, cloud sync, remote analytics, or server-side processing is introduced.

## Consequences

This contract makes unsupported information visible and allows one client to preserve another client's typed receipts without recalculating them. The current workspace may use profile A while profile B remains the global default for a future period. A target can retain either context while its calculator reports a specific activation review. A target without a private original-file store refuses any file containing original attachments. Historical records are retained in typed form only when the target can preserve them exactly.

Separate benefit receipts, weekly-review receipts, crew rule origins/templates, resolution events, agreement extraction/review workflow state, and financial drafts are outside v1. A source containing them refuses export. The envelope and schema do not establish authorship, legal applicability, entitlement, or professional review.

## Native adapter storage

The candidate iOS schema 12 stores optional current-workspace ownership separately from the saved global profile: period ID, profile ID and optional source name. Exact rules, cadence, timezone and currency remain owned by the period; they are not duplicated in that identity record. Legacy decoding leaves the optional metadata absent and retains existing native behavior. Current-workspace and future-default activation are evaluated independently. Adopting current A as C keeps saved future default B unless the worker separately selects the make-default option. If no compatible future default is available, closing a period must not invent the next period or reuse an incompatible profile.

The candidate Android schema 5 may retain a complete typed source archive while leaving its native profile/work projection unavailable. High-precision values, missing source context and unsupported work remain exact read-only evidence until explicit native configuration/adoption; native money/input limits are not widened. A compatible current A remains usable independently of an incompatible future B. A closed or explicitly noncurrent profile pointer cannot become an editable current workspace, and future rule plans do not extend work-time bounds. Starting a separate empty native ledger is an explicit choice when source work cannot safely be copied.

These adapter decisions require migration, persistence/relaunch, independent-context, adoption/default-choice, frozen-history and real provider tests. Earlier test receipts from before the corresponding source changes do not clear those gates.

## Contract-gate evidence

The independent standard-library gate uses synthetic data only:

- `python3 shared/contracts/portable-state/verify.py check`
- `python3 -m unittest discover -s shared/contracts/portable-state/tests -p 'test_*.py'`

`common-weekly-pending.json` verifies a five-shift pending receipt. `adoption-before.json` and `adoption-after.json` verify source-record immutability and stable IDs across a separately confirmed profile adoption. `attachment-valid.json` exercises original-byte integrity and target refusals. Repeating-trace regression strings are based on iOS `PayCalculator`'s exact `Decimal` division by 3,600 and `NSDecimalNumber.stringValue`; they cover one second, one minute, a minimum admitted rate, and a 38-significant-digit difference after the 28th digit. Additional regressions resolve changed rule snapshots for target capability review, accept a future rule change at a period's exclusive end, and keep over-precision selected rule values read-only while preserving the file. The verifier uses an explicit 256-digit local `Decimal` context for validation arithmetic. These checks validate the contract; they do not prove any iOS, Android, or Web runtime adapter, UI, storage migration, atomic replacement, or cross-client device journey.
